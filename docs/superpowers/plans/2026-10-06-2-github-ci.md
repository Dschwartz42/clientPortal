# Client Portal — Plan 2 of 5: GitHub and CI Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The repo is on GitHub, a CI workflow runs the backend lint, migrations and tests on every PR, and `main` is protected so nothing merges without a green check.

**Architecture:** One workflow file, `ci.yml`, with one job per stack. This plan adds the `backend` job; Plan 4 adds the `frontend` job. CI creates the two DB roles with the same `ci_db_setup.sql` that Docker Compose uses locally.

**Tech Stack:** GitHub Actions, `postgres:16` service container, `gh` CLI.

**Spec:** `client-portal-spec.md` — section 10.1.

**Sequence:** Requires Plan 1 complete on local `main`. This plan's PR is merged PR #1 of the "at least 3 merged PRs" in the definition of done.

## Global Constraints

- CI triggers: `pull_request` to `main` and `push` to `main`.
- Backend job, in order: `ruff check .`, `ruff format --check .`, `alembic upgrade head`, `pytest --cov=app --cov-fail-under=80`.
- Python 3.12, pip cache enabled.
- No secrets in CI: the test database passwords are throwaway values in `ci_db_setup.sql`.
- `main` requires a PR and passing CI before merge.

## Review Focus

Checked; this plan adds no runtime behaviour. Two operational conditions are pinned by steps below:

1. A failing test must block the merge → Task 2 Step 4 proves it with a deliberately red PR.
2. CI must exercise RLS as `portal_app`, not as a superuser → Task 2 Step 3 checks that `test_tests_run_as_the_app_role` ran and passed in the CI log.

### Task 2: CI workflow, landed through a PR

**Files:**
- Create: `.github/workflows/ci.yml`

- [ ] **Step 1: Write the workflow on a branch**

```bash
git switch -c ci/backend-workflow
mkdir -p .github/workflows
```

`.github/workflows/ci.yml`:

```yaml
name: CI

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

jobs:
  backend:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: backend
    services:
      postgres:
        image: postgres:16
        env:
          POSTGRES_PASSWORD: postgres
        ports:
          - 5432:5432
        options: >-
          --health-cmd "pg_isready -U postgres"
          --health-interval 5s
          --health-timeout 3s
          --health-retries 10
    env:
      # alembic upgrade head and pytest both target the test database in CI.
      DATABASE_URL: postgresql+psycopg://portal_app:app_pw@localhost:5432/portal_test
      MIGRATION_DATABASE_URL: postgresql+psycopg://portal_owner:owner_pw@localhost:5432/portal_test
      JWT_SECRET: ci-secret-0123456789-0123456789-0123456789
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip
          cache-dependency-path: backend/pyproject.toml
      - name: Install dependencies
        run: pip install -e ".[dev]"
      - name: Create database roles and test database
        run: psql -h localhost -U postgres -v ON_ERROR_STOP=1 -f scripts/ci_db_setup.sql
        env:
          PGPASSWORD: postgres
      - name: Lint
        run: ruff check .
      - name: Format check
        run: ruff format --check .
      - name: Migrate
        run: alembic upgrade head
      - name: Test
        run: pytest -v --cov=app --cov-fail-under=80
```

- [ ] **Step 2: Open the PR**

```bash
git add .github/workflows/ci.yml
git commit -m "ci: run backend lint, migrations and tests on every PR"
git push -u origin ci/backend-workflow
gh pr create --title "ci: backend lint, migrations and tests" --body "Adds the CI workflow from spec section 10.1 (backend job). Frontend job follows with the frontend."
```

- [ ] **Step 3: Verify the run**

Run: `gh pr checks --watch`
Expected: `backend` passes.

Run: `gh run view --log | grep -E "test_tests_run_as_the_app_role|TOTAL"`
Expected: `test_tests_run_as_the_app_role PASSED` and a `TOTAL` coverage line ≥ 80%.

If the run fails, fix on the same branch and push again. Do not merge red.

- [ ] **Step 4: Prove a failing test blocks the PR**

```bash
git switch -c ci/prove-red
printf '\n\ndef test_deliberately_red():\n    assert False\n' >> backend/tests/unit/test_security.py
git commit -am "test: deliberately failing test (do not merge)"
git push -u origin ci/prove-red
gh pr create --title "DO NOT MERGE: prove CI goes red" --body "Demonstrates a failing test blocks the pipeline."
gh pr checks --watch
```

Expected: `backend` fails. Then discard it:

```bash
gh pr close --delete-branch
git switch ci/backend-workflow
```

This closed PR is useful evidence for interview question 13 ("what happens if a test fails on a PR?").

- [ ] **Step 5: Merge**

```bash
gh pr merge ci/backend-workflow --squash --delete-branch
git switch main && git pull
```

### Task 3: Protect `main`

- [ ] **Step 1: Require a PR and the `backend` check**

```bash
REPO=$(gh repo view --json nameWithOwner -q .nameWithOwner)
gh api -X PUT "repos/$REPO/branches/main/protection" --input - <<'JSON'
{
  "required_status_checks": { "strict": false, "contexts": ["backend"] },
  "enforce_admins": true,
  "required_pull_request_reviews": { "required_approving_review_count": 0 },
  "restrictions": null
}
JSON
```

`required_approving_review_count: 0` requires a PR without requiring a second person to approve it (solo project). Plan 4 adds `frontend` to `contexts`.

- [ ] **Step 2: Verify direct pushes are rejected**

```bash
git commit --allow-empty -m "chore: should be rejected" && git push
```

Expected: push rejected with a protected-branch error. Clean up: `git reset --hard origin/main`.

**Plan 2 done when:** PR #1 is merged with a green `backend` check and direct pushes to `main` are refused. From here on, every plan works on a feature branch and merges through a PR.
